## 0. What was measured, and against what

**The baseline is `evidence/M3/after`**, named rather than re-derived, as the contract requires. It
is the matrix M3 left behind; the zero-delta gate in part 2 is computed against it.

**And it is not enough for this task**, which is the first finding of the record.

> **M7-F01 — no two `stats` cells in the matrix show the same screen, and the difference is the
> ORDER of the matrix rather than the size or the language.**
>
> **This finding was first written down wrong, and the correction is the interesting half.** The
> single number that started it is right: the FIRST `stats` cell — `de/1920x1080`, the first surface
> of the first pass — carries **171 nodes** against the hub's **163**, i.e. the empty screen. From
> that I concluded the cell had *always* been empty, because the survey starts from a fresh profile.
>
> Counting the rest says otherwise. `evidence/M3/after`, `stats`, in matrix order:
>
> | cell | de/1920 | de/1600 | de/1536 | de/1400 | de/1280 | en/1920 | en/1600 | en/1536 | en/1400 | en/1280 |
> | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
> | nodes | **171** | 276 | 295 | 306 | 317 | 328 | 339 | 350 | 368 | 379 |
>
> Monotone, and about eleven nodes — one run row — per step. The cause: `seedScript` writes
> `as_options` and `as_username` and **never clears `as_runhistory`**, and the `victory` cell of
> every pass ends a run, which `recordRun` appends to the history. So the statistics screen the
> matrix holds has **zero** runs in the first cell and **nine** in the last.
>
> Consequences, and they cut both ways:
>
> * **The before/after comparison is sound.** Both survey runs walk the same 160 cells in the same
>   order with a seeded `Math.random`, so cell *n* holds the same number of runs in both. That is
>   why the gate below is readable at all.
> * **Reading the matrix ACROSS cells is not.** Comparing `stats` at 1280×720 with `stats` at
>   1920×1080 in that matrix compares a four-run screen with an empty one. Anyone measuring this
>   screen from the matrix — a text-shrinkage criterion, an overflow count, a node census — is
>   comparing two different screens and cannot see it.
> * **It is not a defect in the survey's contract**, which promises a surface in its resting state
>   and delivers exactly that. It is an unregistered state dependency, and the contract's own hazard
>   table names `stats` as the state-dependent surface — for the reader's profile, not for the
>   matrix's own order.
>
> Both of the cell's markers were state-dependent too: `.st-sec` renders only with history, and
> `.st-readout` was the readout line the Kopf-Kanon dissolves. The marker is `.st-head` now — the one
> node that exists whenever the screen is open, empty or not.
>
> **This is why the geometry of the two screens is measured by a second harness against a named
> profile**, and why that decision is not a preference.

So the geometry of the two redesigned screens is measured by a second harness, in the same
production build, at the same five sizes, in both languages:

| | |
| --- | --- |
| Harness | `evidence/M7/measure.mjs` — production build, real CDP viewport, **port 5189** |
| Profile | `evidence/M7/seed.mjs` — generated, deterministic, twelve runs |
| Before | `evidence/M7/before/geometry.json` (base `d4870e5f`) |
| After | `evidence/M7/after-geometry/geometry.json` (this branch) |

**Port hygiene.** 5181 was verified free before the survey and 5189 before every geometry run.
The one thing found there is worth recording: a **stale `vite preview` from an earlier session was
still holding 5189**, serving an unknown `dist`. `measure.mjs` therefore *refuses* to run when
something already answers on its port, rather than reusing it — the failure mode that cost M3 its
gate, made impossible instead of remembered.

### The seeded profile — hazard H-e, answered in code

`stats` reads accumulated history: its node set, its section heights and its very existence depend
on `as_runhistory`. Two halves of a comparison taken against two different profiles are not a
comparison. The profile is therefore **generated from `seed.mjs`**, with no `Date.now()`, no
`Math.random()` and no run-time timestamps — re-running it produces a byte-identical blob.

| | |
| --- | --- |
| Runs | **12** — the design document's own stated measurement basis, and above `MIN_SAMPLE` (8) so the evaluation section shows its populated, taller form |
| Run 0 | **the full run** — 7 skills (`SKILL_SLOTS` 6 + one legendary), 20 flat perks, a 40-card snapshot, four architect buildings across all three categories, a 13-point trajectory and a 9-cycle trick log |
| Run 6 | **the thin run** — no snapshot, no trajectory, no trick log: the quota path (`storage.js:398`) and the foreign-board case |
| Rest | ordinary runs, enough of each archetype that `bestArchetype` (minRuns 3) and `scoreLift` (minWith 3 plus one run without) both return something |
| Totals | best 1 284 000 · games 12 · every id read from the real registries, none invented |

Two things the seeding cost, both worth the next person's time:

> **M7-F02 — a seeded profile does not survive its first boot, silently.**
> `maybeResetForEpoch` (`storage.js:329`) runs once per namespace in every deployed build and calls
> `wipeProfileStorage()` unless `as_reset_epoch` already holds `RESET_EPOCH`. The first run of this
> harness measured a fully seeded profile and got the empty screen in all ten cells — nothing
> errored, the numbers were simply of a different screen. The seed carries the stamp now, and
> `measure.mjs` **throws** when the run list comes back empty rather than writing a file.

> **M7-F03 — a synthetic Escape closes two layers, not one.**
> `useEscape` is mounted by the statistics screen as well as by the run window, and the window is a
> portal on `document.body`: one key event reaches both listeners. The harness clicks the window's
> own close button instead, which is what a player's Escape actually does.

> **The clause is met: `run-stage` at zero deltas, printed rather than claimed.** And the gate says
> more than the clause asks. `victory` renders **all three** shared components — `RunStats`,
> `RunGraphs` **and** `Sparkline`, the last of them at three sites — and it is at zero too. Fifteen
> of sixteen surfaces did not move by one pixel or one colour.

**The sixteenth is `stats`, by design.** It is a tier-C task: the tree changed on purpose, so 844
structural paths no longer line up between the two runs and the comparator reports them as
unmatched. The 112 nominal deltas are on that same surface and are the redesign itself — the card
clamping (592.1 → 698 at 1280×720), the head growing (62.1 → 122.3), and the sections gaining the
panel surface, the deck frame and the panel radius (`rd` 6 → 14, `bc` from the translucent neutral
to the 26 % deck mix). **Nothing outside `stats` moved at all**, which is the stronger statement and
the one the acceptance gate turns on.

**One token differs in declared text, and it is diagnostic rather than a delta:**
`--ed-deck-panel: (absent) → color-mix(in srgb, #26c6e6 26%, #9696aa29)`, in all 160 cells. It was
defined in the annex at the freeze and had **no call site**, so Tailwind pruned it from the built
stylesheet (`2c`: *a token you do not use does not ship*). Using it is what brings it back. No
element row changed because of it outside `stats`.

**One thing the gate cannot see, and it says so on every run:** *„Surfaces only. Control states are
not captured and are verified by hand."* Ten states were driven by hand — §4 below.

**The run window is not in this matrix at all**, and that is not something this task closed: no
survey cell opens it, and it is a named gap in `survey-findings.md` §4. Everything measured about it
comes from `evidence/M7/after-geometry/` and from the state walk.

**This survey was re-run after the last code change** rather than reused: an earlier pass had
already produced the same 112/844 result, and the run was repeated because `.st-runs` and
`.st-picked2` changed afterwards (the run list was measuring its own content instead of its column —
§3.2). Both runs agree; the one committed is the one that matches the shipped build.

**„Die drei Spalten enden 305 px auseinander" is answered for the two that were the complaint.**
Columns 2 and 3 — the run list and the choice behaviour — ran 304.8 px apart (686.75 against 991.56)
and now end on the same line at every size. Column 1 is a **stack**, so it ends where its content
ends and its slack sits at its foot: 78.1 px below the row at 1280×720 (where it overflows into the

than a residue — *„Restluft sammelt sich am Fuß einer Spalte, nie zwischen zwei Panels"* — and it is
the difference between an unequal edge and a gap in the middle of a column.

**The run list fills its column**, which is the one place where the measurement had to be repaired
rather than read: without `flex: 1 1 auto` the list took its own CONTENT height, so `useRunCap`
measured itself and reported „ten fit" into a 738-px column at 1920×1080 that carries fourteen. A
feedback loop that happens to be stable at ten is not a measurement. With the block filling its
column — and `align-content: start`, or the grid stretches the 44-px targets to 63.8 px — the list
shows **12 of 12 stored runs without scrolling at 1920×1080**, 11 at 1600×900, and 10 below that.

where it has to: 1.14× at 1280×720, 1.18× at 1400×700 (the flattest window), 1.01× at 1536×791,
