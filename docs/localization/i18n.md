# Zweisprachigkeit — wie Autostich Texte hält

**Kurzfassung für jeden Zugang:** Ein neuer Anzeigetext gehört in `src/i18n/de.js` **und**
`src/i18n/en.js`. Nichts anderes. Die Tests erzwingen den Rest.

---

## 1. Warum überhaupt eine Schicht

Die naheliegende Antwort auf „wo stehen unsere Texte?" ist ein gepflegtes Dokument. Genau das
ist die Fehlerform, die die Sprachprüfung im August 2026 aufgedeckt hat: die Texte, die still
von der Mechanik weggedriftet waren, waren **alle** handgepflegt —

- „Meisterrang" als Freischalt-Bedingung, obwohl der Meister-Modus längst durch die
  Wochen-Rangliste ersetzt war,
- „Ungewöhnlich" als Raritätsname, den es im Code nicht gab,
- eine Trimmliste mit 4 von 6 trimmbaren Skills,
- drei auseinandergelaufene Fassungen desselben Gebäude-Effekttextes.

Ein handgepflegtes Dokument ist ein **zweiter Wahrheitsort**. Zwei Wahrheitsorte driften — immer,
nur die Frage ist wann. Mit einer zweiten Sprache verdoppelt sich das Risiko.

So lösen es andere Spiele, und so lösen wir es auch:

| Engine / Stack | Quelle | Dokument |
|---|---|---|
| Unity | String Tables (Asset) | CSV/XLIFF-**Export** |
| Unreal | `.po`-Katalog, „Gather from source" | `.po`-**Export** |
| Godot | Übersetzungs-CSV → `.translation` | dieselbe CSV, **importiert** |
| i18next / FormatJS | `de.json` / `en.json` | TMS-**Export** (Crowdin, Lokalise) |
| **Autostich** | `src/i18n/de.js` / `en.js` | `docs/localization/strings_*.csv` — **erzeugt** |

Die Regel überall dieselbe: **Katalog im Code = Quelle. Dokument = erzeugte Ansicht.**
Das Dokument wird nie von Hand angefasst; es entsteht aus `npm run loc:export`.

## 2. Warum JS-Module und nicht `de.json`

Weil die Tuning-Zahlen im Text stehen. `„Kritische Treffer geben ×2,25"` wird aus
`CRIT_BASE_MULT` interpoliert; über 50 solcher Stellen ziehen ihre Zahl aus `constants.js` oder
`glacier.js`. In JSON müssten sie als tote Literale einfrieren — genau der Drift, den wir gerade
beseitigt haben. Ein JS-Katalog kann `import` und Template-Literale und bleibt trotzdem
schlüsselbasiert (Parität testbar, CSV-Export unverändert möglich).

Das ist der einzige bewusste Unterschied zum Industriestandard, und er ist begründet.

## 3. Die Bestandteile

```
src/i18n/index.js     t(), Sprachzustand, Zahlformate — React-frei, auch aus src/game/ nutzbar
src/i18n/useLocale.js React-Anschluss: useT(), useLocale()
src/i18n/de.js        Katalog Deutsch (Ausgangssprache)
src/i18n/en.js        Katalog Englisch
test/i18n-guards.test.js  die Wächter (siehe §5)
scripts/export-strings.mjs → docs/localization/strings_*.csv  (Ansicht, nicht Quelle)
```

```
src/i18n/labels.js    Leser für migrierte Register (rarityLabel, formationName, formationAbbr)
```

Die gewählte Sprache liegt in den Optionen (`options.lang`, `src/game/storage.js`). `null` heißt
„noch nie gewählt" → es gilt `DEFAULT_LOCALE` (Englisch), und der Spieler wählt beim ersten Start
selbst (§6). `App.jsx` setzt sie vor dem ersten Rendern und spiegelt sie in `<html lang>`.

## 4. So schreibt man einen Text

```js
// de.js
"start.resume.sub": "Durchlauf {cycle}/{total} · Score {score}",
// en.js
"start.resume.sub": "Cycle {cycle}/{total} · Score {score}",
```

```jsx
import { fmtNum } from "../i18n/index.js";
import { useT } from "../i18n/useLocale.js";

const t = useT();
t("start.resume.sub", { cycle: 3, total: 50, score: fmtNum(1234567) })
```

**Regeln**

- Schlüssel: `<bereich>.<block>.<sache>`, klein, Punkt-getrennt. Nie ein ganzer Satz als Schlüssel.
- Laufzeit-Zahlen kommen als Platzhalter `{name}` rein, nie fest in den Text.
- Zahlen immer durch `fmtNum` / `fmtPct` — Deutsch schreibt `1.234,5`, Englisch `1,234.5`.
  Kein `toLocaleString("de-DE")` mehr.
- Tuning-Zahlen aus den Konstanten interpolieren (Template-Literal im Katalog), nie abtippen.
- Plural über das Paar `…_one` / `…_other`, ausgewählt durch die Variable `count`.
- Auch `title`, `aria-label`, `placeholder` und `alt` sind Anzeigetexte.
- Begriffe folgen `uebersetzerpaket_pixi_2026-08-15.md` §3: eine deutsche Vokabel → **genau eine**
  englische. `Durchlauf` ist `cycle`, nie `round`. `Stich` ist `trick`, nie `round`.

## 5. Was die Tests erzwingen

`test/i18n-guards.test.js` läuft über den Katalog, nicht über eine Handliste — es wächst also
ohne Pflege mit. Es macht den Deploy rot bei:

1. **Schlüssel-Parität** — ein Text existiert nur in einer Sprache.
2. **Platzhalter-Parität** — `{score}` fehlt in der Übersetzung, die Zahl verschwände spurlos.
3. **Vergessene Übersetzung** — der englische Eintrag ist Wort für Wort der deutsche. Echte
   Ausnahmen (Eigennamen, „Score", „DP") stehen namentlich in `SAME_OK`.
4. **Zahlformat** — deutsches Dezimalkomma im englischen Katalog und umgekehrt.
5. **Anführungszeichen** — `„…“` im Deutschen, `“…”` im Englischen.
6. **Plural-Paare** — `…_one` ohne `…_other`.
7. **Terminologie** — die Begriffstabelle §3 als Regex-Liste, in beide Richtungen
   (richtiges Wort verwendet **und** verbotenes Synonym vermieden).
8. **Ratsche** — in bereits migrierten Dateien darf **kein** Anzeigetext mehr fest verdrahtet
   sein. Die Liste `MIGRATED` wächst und schrumpft nie.
9. **Tote Schlüssel** — ein Katalogeintrag, den kein `t()` aufruft.

Punkt 8 ist der eigentliche Mechanismus für die Frage „wie stellen wir sicher, dass immer eine
englische Variante mitkommt": nicht Disziplin, sondern ein Test, der beim nächsten `npm test`
fehlschlägt. Die CI-Workflows fahren `npm ci → npm test → npm run build`, ein roter Test
blockiert also den Deploy.

## 6. Sprachwahl im Spiel — wo der Spieler umschaltet

Zwei Orte, mehr nicht:

1. **Beim allerersten Start**, im Namens-Dialog unter dem Eingabefeld. Das ist der einzige Moment,
   in dem jeder Spieler garantiert vorbeikommt. Die Umschaltung wirkt **sofort** — der Dialog
   wechselt mit —, damit man das Ergebnis der Wahl sieht, bevor man weiterklickt.
2. **Danach in den Optionen** unter „Sprache / Language".

Die Sprachnamen stehen bewusst in ihrer **eigenen** Sprache („Deutsch" / „English"): Wer die
gerade aktive Sprache nicht lesen kann, findet trotzdem seine.

**Der Auslieferungs-Standard ist Englisch.** Zwei Begriffe, die gern verwechselt werden und
deshalb in `index.js` getrennt sind:

| | Wert | Bedeutung |
|---|---|---|
| `SOURCE_LOCALE` | `de` | Sprache, in der geschrieben wird. Ihr Katalog ist immer vollständig → Rückfall bei fehlendem Schlüssel. |
| `DEFAULT_LOCALE` | `en` | Was ein neuer Spieler bekommt, solange er nichts gewählt hat. |

Die **Browsersprache wird bewusst nicht befragt**. Sie zu befragen hieße, dass ein deutscher
Browser automatisch Deutsch bekommt — dann wäre Englisch nicht der Standard, sondern eine
Zufallsfunktion des Geräts. Gespeichert wird in `options.lang`; `null` = noch nie gewählt.

### Das Muster für Register (an Rarität + Formationen erprobt)

Drei Regeln, die zusammen dafür sorgen, dass kein deutscher Text zweimal existiert:

1. **Das Register bleibt die Quelle des deutschen Texts.** `rarity.js` und `constants.js` ändern
   sich nicht.
2. **`de.js` ERZEUGT seine Einträge daraus** (`for (const m of Object.values(TIER_META)) …`).
   Damit kann die deutsche Seite gar nicht vom Register wegdriften; abgetippt wird nichts.
   `en.js` schreibt die Übersetzung von Hand — die Schlüssel-Parität im Guard erzwingt Vollständigkeit.
3. **Aufgelöst wird zur Anzeigezeit** über `src/i18n/labels.js` (`rarityLabel`, `formationName`,
   `formationAbbr`). Ein Modul-Level-Objekt fröre die Sprache beim Laden ein — deshalb ist auch
   `formationTypes()` eine Funktion, keine Konstante.

**Warum `labels.js` und nicht direkt im Register?** Weil `de.js` die Register importiert. Ein
`import { t }` in `rarity.js` wäre ein Zyklus (`de.js → rarity.js → i18n/index.js → de.js`). Die
Register bleiben Blätter; alles, was übersetzt, liegt eine Schicht darüber.

**Reihenfolge für den Rest:** Erst die Register, deren Namen in FREMDE Texte eingesetzt werden
(Rarität und Formationen — erledigt, deshalb zuerst), dann die selbsttragenden (Skills, Perks,
Familien, Gebäude), zuletzt das Glossar. Das Glossar ist der Sonderfall: seine Texte werden beim
Modul-Laden als Template-Literale gebaut, es muss also gleichzeitig auf lazy umgestellt werden.

## 7. Werkzeug

```
npm run loc:export     # CSV neu erzeugen (docs/localization/strings_*.csv)
npm test               # inkl. i18n-Guards
```

Die CSV hat drei Zeilenarten: `status=done` (aus dem Katalog, beide Sprachen gefüllt),
`status=new` (noch nicht migriert, `en` leer) und die Glossar-`match`-Zeilen (Wortformen für die
Auto-Fettung — die müssen für Englisch **neu geschrieben**, nicht übersetzt werden).
