# Mehrsprachigkeit — wie Autostich Texte hält

**Kurzfassung für jeden Zugang:** Ein neuer Anzeigetext gehört in `src/i18n/de.js` **und**
`src/i18n/en.js`. Nichts anderes. Die Tests erzwingen den Rest.

Seit dem 26.08.2026 kennt der Code eine dritte Sprache (`es`), die noch nicht ausgeliefert wird.
An der Kurzfassung ändert das nichts: gepflegt werden weiter genau die zwei fertigen Kataloge, und
für die unfertige gilt eine eigene Regel (§6).

---

## 1. Warum überhaupt eine Schicht

Die naheliegende Antwort auf „wo stehen unsere Texte?" ist ein gepflegtes Dokument. Genau das
ist die Fehlerform, die die Sprachprüfung im August 2026 aufgedeckt hat: die Texte, die still
von der Mechanik weggedriftet waren, waren **alle** handgepflegt —

- „Meisterrang" als Freischalt-Bedingung, obwohl der Meister-Modus längst durch die
  Wochen-Rangliste ersetzt war,
- „Ungewöhnlich" als Raritätsname, den es im Code nicht gab,
- eine Trimmliste mit 4 von 6 trimmbaren Skills,
- drei auseinandergelaufene Fassungen desselben Gebäude-Effekttextes.

Ein handgepflegtes Dokument ist ein **zweiter Wahrheitsort**. Zwei Wahrheitsorte driften — immer,
nur die Frage ist wann. Mit einer zweiten Sprache verdoppelt sich das Risiko.

So lösen es andere Spiele, und so lösen wir es auch:

| Engine / Stack | Quelle | Dokument |
|---|---|---|
| Unity | String Tables (Asset) | CSV/XLIFF-**Export** |
| Unreal | `.po`-Katalog, „Gather from source" | `.po`-**Export** |
| Godot | Übersetzungs-CSV → `.translation` | dieselbe CSV, **importiert** |
| i18next / FormatJS | `de.json` / `en.json` | TMS-**Export** (Crowdin, Lokalise) |
| **Autostich** | `src/i18n/de.js` / `en.js` | `docs/localization/strings_*.csv` — **erzeugt** |

Die Regel überall dieselbe: **Katalog im Code = Quelle. Dokument = erzeugte Ansicht.**
Das Dokument wird nie von Hand angefasst; es entsteht aus `npm run loc:export`.

## 2. Warum JS-Module und nicht `de.json`

Weil die Tuning-Zahlen im Text stehen. `„Kritische Treffer geben ×2,25"` wird aus
`CRIT_BASE_MULT` interpoliert; über 50 solcher Stellen ziehen ihre Zahl aus `constants.js` oder
`glacier.js`. In JSON müssten sie als tote Literale einfrieren — genau der Drift, den wir gerade
beseitigt haben. Ein JS-Katalog kann `import` und Template-Literale und bleibt trotzdem
schlüsselbasiert (Parität testbar, CSV-Export unverändert möglich).

Das ist der einzige bewusste Unterschied zum Industriestandard, und er ist begründet.

## 3. Die Bestandteile

```
src/i18n/index.js     t(), Sprachzustand, Zahlformate — React-frei, auch aus src/game/ nutzbar
src/i18n/useLocale.js React-Anschluss: useT(), useLocale()
src/i18n/de.js        Katalog Deutsch (Ausgangssprache)
src/i18n/en.js        Katalog Englisch
test/i18n-guards.test.js  die Wächter (siehe §5)
scripts/export-strings.mjs → docs/localization/strings_*.csv  (Ansicht, nicht Quelle)
```

```
src/i18n/labels.js    Leser für migrierte Register (rarityLabel, formationName, formationAbbr)
```

Die gewählte Sprache liegt in den Optionen (`options.lang`, `src/game/storage.js`). `null` heißt
„noch nie gewählt" → es gilt `DEFAULT_LOCALE` (Englisch), und der Spieler wählt beim ersten Start
selbst (§6). `App.jsx` setzt sie vor dem ersten Rendern und spiegelt sie in `<html lang>`.

## 4. So schreibt man einen Text

```js
// de.js
"start.resume.sub": "Durchlauf {cycle}/{total} · Score {score}",
// en.js
"start.resume.sub": "Cycle {cycle}/{total} · Score {score}",
```

```jsx
import { fmtNum } from "../i18n/index.js";
import { useT } from "../i18n/useLocale.js";

const t = useT();
t("start.resume.sub", { cycle: 3, total: 50, score: fmtNum(1234567) })
```

**Regeln**

- Schlüssel: `<bereich>.<block>.<sache>`, klein, Punkt-getrennt. Nie ein ganzer Satz als Schlüssel.
- Laufzeit-Zahlen kommen als Platzhalter `{name}` rein, nie fest in den Text.
- Zahlen immer durch `fmtNum` / `fmtPct` — Deutsch schreibt `1.234,5`, Englisch `1,234.5`.
  Kein `toLocaleString("de-DE")` mehr.
- Tuning-Zahlen aus den Konstanten interpolieren (Template-Literal im Katalog), nie abtippen.
- Plural über das Paar `…_one` / `…_other`, ausgewählt durch die Variable `count`.
- Auch `title`, `aria-label`, `placeholder` und `alt` sind Anzeigetexte.
- Begriffe folgen `uebersetzerpaket_pixi_2026-08-15.md` §3: eine deutsche Vokabel → **genau eine**
  englische. `Durchlauf` ist `cycle`, nie `round`. `Stich` ist `trick`, nie `round`.

## 5. Was die Tests erzwingen

`test/i18n-guards.test.js` läuft über den Katalog, nicht über eine Handliste — es wächst also
ohne Pflege mit. Es macht den Deploy rot bei:

1. **Schlüssel-Parität** — ein Text existiert nur in einer Sprache.
2. **Platzhalter-Parität** — `{score}` fehlt in der Übersetzung, die Zahl verschwände spurlos.
3. **Vergessene Übersetzung** — der englische Eintrag ist Wort für Wort der deutsche. Echte
   Ausnahmen (Eigennamen, „Score", „DP") stehen namentlich in `SAME_OK`.
4. **Zahlformat** — deutsches Dezimalkomma im englischen Katalog und umgekehrt.
5. **Anführungszeichen** — `„…“` im Deutschen, `“…”` im Englischen.
6. **Plural-Paare** — `…_one` ohne `…_other`.
7. **Terminologie** — die Begriffstabelle §3 als Regex-Liste, in beide Richtungen
   (richtiges Wort verwendet **und** verbotenes Synonym vermieden).
8. **Ratsche** — in bereits migrierten Dateien darf **kein** Anzeigetext mehr fest verdrahtet
   sein. Die Liste `MIGRATED` wächst und schrumpft nie.
9. **Tote Schlüssel** — ein Katalogeintrag, den kein `t()` aufruft.

Punkt 8 ist der eigentliche Mechanismus für die Frage „wie stellen wir sicher, dass immer eine
englische Variante mitkommt": nicht Disziplin, sondern ein Test, der beim nächsten `npm test`
fehlschlägt. Die CI-Workflows fahren `npm ci → npm test → npm run build`, ein roter Test
blockiert also den Deploy.

## 6. Sprachwahl im Spiel — wo der Spieler umschaltet

Zwei Orte, mehr nicht:

1. **Beim allerersten Start**, im Namens-Dialog unter dem Eingabefeld. Das ist der einzige Moment,
   in dem jeder Spieler garantiert vorbeikommt. Die Umschaltung wirkt **sofort** — der Dialog
   wechselt mit —, damit man das Ergebnis der Wahl sieht, bevor man weiterklickt.
2. **Danach in den Optionen** unter „Sprache / Language".

Die Sprachnamen stehen bewusst in ihrer **eigenen** Sprache („Deutsch" / „English" / „Español"):
Wer die gerade aktive Sprache nicht lesen kann, findet trotzdem seine. Beide Wähler bemessen ihre
Spaltenzahl an der Anzahl der fertigen Sprachen, nicht an einer festen Zwei.

**Der Auslieferungs-Standard ist Englisch.** Drei Begriffe, die gern verwechselt werden und
deshalb in `index.js` getrennt sind:

| | Wert | Bedeutung |
|---|---|---|
| `SOURCE_LOCALE` | `de` | Sprache, in der geschrieben wird. Ihr Katalog ist immer vollständig → letzter Rückfall bei fehlendem Schlüssel. |
| `DEFAULT_LOCALE` | `en` | Was ein neuer Spieler bekommt, solange er nichts gewählt hat. |
| `LOCALE_IDS` vs. `READY_LOCALE_IDS` | `de en es` vs. `de en` | **angemeldet** vs. **auslieferbar** — siehe unten. |

### Angemeldet ist nicht ausgeliefert (#es-locale)

Seit dem 26.08.2026 kennt der Code eine dritte Sprache, `es`. Sie trägt `ready: false` und ist damit
**nicht wählbar**: die Wähler bieten sie nicht an, und `setLocale("es")` weist sie ab wie eine
unbekannte Sprache — auch dann, wenn ein altes `options.lang` sie noch enthielte.

Der Sinn der Trennung: Formatierer, Wächter und Export kennen die Sprache von Anfang an, ohne dass
ein halb übersetzter Katalog vor einen Spieler kommt. Die Wächter folgen dabei einer Regel, keiner
Sprachliste:

- **verbietende** Prüfungen laufen über **alle** angemeldeten Sprachen (verwaiste Schlüssel, kaputte
  Platzhalter, leerer Text, fremdes Dezimal- oder Anführungszeichen, halbe Plural-Paare),
- **verlangende** Prüfungen laufen über die **fertigen** (Schlüssel-Parität, Ein-Zeichen-Kürzel,
  Glossar-Wortformen).

Damit die Ausnahme nicht liegen bleibt, gibt es eine Ratsche: **sobald ein `ready: false`-Katalog
Schlüssel-Parität erreicht, wird die Suite rot** und verlangt `ready: true`. Eine fertig übersetzte,
aber unerreichbare Sprache kann es also nicht geben.

### Die Rückfallkette

`SOURCE_LOCALE` ist der **letzte** Rückfall, nicht der einzige. Jede Sprache darf mit `via` eine
Kette davor setzen; `es` hat `via: ["en"]`. Ohne sie zeigte ein fehlender spanischer Schlüssel einem
spanischen Spieler **Deutsch** statt Englisch — der Grund, warum die Kette überhaupt existiert.

Die **Browsersprache wird bewusst nicht befragt**. Sie zu befragen hieße, dass ein deutscher
Browser automatisch Deutsch bekommt — dann wäre Englisch nicht der Standard, sondern eine
Zufallsfunktion des Geräts. Gespeichert wird in `options.lang`; `null` = noch nie gewählt.

### Das Muster für Register (an Rarität + Formationen erprobt)

Drei Regeln, die zusammen dafür sorgen, dass kein deutscher Text zweimal existiert:

1. **Das Register bleibt die Quelle des deutschen Texts.** `rarity.js` und `constants.js` ändern
   sich nicht.
2. **`de.js` ERZEUGT seine Einträge daraus** (`for (const m of Object.values(TIER_META)) …`).
   Damit kann die deutsche Seite gar nicht vom Register wegdriften; abgetippt wird nichts.
   `en.js` schreibt die Übersetzung von Hand — die Schlüssel-Parität im Guard erzwingt Vollständigkeit.
3. **Aufgelöst wird zur Anzeigezeit** über `src/i18n/labels.js` (`rarityLabel`, `formationName`,
   `formationAbbr`). Ein Modul-Level-Objekt fröre die Sprache beim Laden ein — deshalb ist auch
   `formationTypes()` eine Funktion, keine Konstante.

**Warum `labels.js` und nicht direkt im Register?** Weil `de.js` die Register importiert. Ein
`import { t }` in `rarity.js` wäre ein Zyklus (`de.js → rarity.js → i18n/index.js → de.js`). Die
Register bleiben Blätter; alles, was übersetzt, liegt eine Schicht darüber.

### Zahlen in übersetzten Registertexten

79 der 84 Skill-Beschreibungen tragen Tuning-Zahlen. Die englischen Texte **tippen sie nicht ab** —
sie benutzen dieselben Ausdrücke wie das deutsche Original (`${C.STATIC_CHARGE}`,
`${pct(C.STORM_CRIT_CAP)}`), gezogen aus denselben Konstanten. Ein Balancing-Schritt bewegt damit
beide Sprachen gleichzeitig.

Weil nichts das *erzwingt*, sichert ein Wächter die Naht ab: **beide Sprachen müssen dieselben
Zahlen nennen** (Zahlmengen extrahieren, Trennzeichen normalisieren, vergleichen). Wer eine Zahl
abtippt, merkt es beim nächsten Tuning sofort. Ausnahmen (eine ausgeschriebene Zahl im Englischen)
stehen namentlich mit Begründung in `NUM_OK`.

Nebenbefund: Der ältere Format-Wächter (`/\d,\d/` im Englischen) schlug auf Tausendertrenner an —
beide Sprachen benutzen beide Zeichen, nur in vertauschten Rollen. Unterscheidungsmerkmal ist die
Blockgröße: ein Tausenderblock hat **genau drei** Ziffern, alles andere ist ein Dezimalteil.

### Die Struktur des Registers mitübersetzen, nicht das Ergebnis

Bei den Familien wäre es ein Fehler gewesen, die 292 gerenderten Stufentexte einzeln zu übersetzen.
Das deutsche Register hat nämlich nur ~120 Quellen dafür: 22 Familien teilen sich je EINEN Satz
(`MUSTER_DESC`, `$0`/`$1` je Stufe), und die fünf Präzisions-Familien entstehen aus indizierten
Konstanten. Der englische Katalog spiegelt **beide Sparmechanismen** — sonst hätte die Übersetzung
292 Pflegestellen erzeugt, wo das Original 120 hat.

Regel daraus: **Übersetze die Struktur des Registers, nicht seine Ausgabe.**

Bei den Architekt-Gebäuden geht dasselbe Prinzip noch einen Schritt weiter: Ihr Effekttext ist gar
kein gepflegter Text, sondern das Ergebnis EINER Generator-Funktion. Übersetzt wurden deshalb die
**Satzbausteine** (`building.eff.*`, `building.kick.*` — rund 35 Schlüssel), nicht die über 100
Endtexte. Der Generator ist dabei von `src/game/architect.js` nach `src/i18n/buildingText.js`
gewandert: Satzvorlagen sind Anzeigetext und gehören in die i18n-Schicht, die Zahlen-Helfer
(`tierNum`/`tierFactor`/`bindSpanFor`) bleiben im Spiel-Layer. Ein `import { t }` in `architect.js`
wäre außerdem ein Zyklus (architect → i18n → de.js → families.js → architect).

In der CSV erscheinen die Effekttexte trotzdem zweisprachig: der Export rendert sie einmal je
Sprache. Der Übersetzer sieht den echten In-Game-Wortlaut, ohne dass daraus ein zweiter Pflegeort wird.

### Funktionen als Katalogeinträge

Die Wochen-Mod-Beschreibungen sind im deutschen Register **Funktionen der gewürfelten Stärke**
(`desc: (v) => \`Gegnerkarten +${v} Wert\``). Der Katalog braucht sie als Vorlage mit Platzhalter —
und bekommt sie, ohne dass jemand sie abtippt: `de.js` ruft die Funktion **mit dem Platzhalter
selbst** auf (`m.desc("{v}")`) und erhält so exakt den Satz mit `{v}` darin. Der Leser
(`weekModList`) gibt `desc` wieder als Funktion zurück, damit die Aufrufstellen unverändert bleiben.

### Der Glossar-Sonderfall: Wortformen schreibt man neu, man übersetzt sie nicht

Jeder Glossareintrag trägt eine `match`-Liste. Das ist **kein Anzeigetext** — sie steuert, welche
Wörter in *jeder* Beschreibung im Spiel fett werden (`tokenizeGlossary`). Die deutsche Liste führt
Flexionen wie „Durchlaufs" und „Durchläufen"; sie zu übersetzen wäre sinnlos. Englisch braucht
**andere** Formen: Plurale, Verbformen („burst / bursts / bursting"), Bindestrich-Varianten. Und
jede Form muss exakt so geschrieben sein, wie sie im englischen Katalog vorkommt — eine Form, die
nie auftaucht, fettet nie.

Dazu kam ein struktureller Fehler, den die Zweisprachigkeit erst sichtbar gemacht hat: Der
Tokenizer verdichtete die Wortformen **einmal beim Modul-Laden** zu einer Regex. Damit hing die
Fettung an der Sprache, die beim Import zufällig aktiv war — ein Sprachwechsel hätte sie nicht
mitbekommen. `tokenizeGlossary` liegt deshalb jetzt in `src/i18n/glossaryText.js` und baut die
Regex **je Sprache** (gecacht: zwei Sprachen, zwei Regexe).

Gemessen nach dem Umbau, über alle 390 Skill-, Familien- und Perk-Texte:

| | Fettungen | ohne Treffer | Roundtrip |
|---|---|---|---|
| Deutsch | 678 | 6 % | verlustfrei |
| Englisch | 738 | 6 % | verlustfrei |

Zwei Wächter sichern das ab: keine leere oder doppelte Wortform, und die Fettung muss in **beiden**
Sprachen verlustfrei sein UND überhaupt greifen (untere Schranke an Treffern). Ohne die zweite
Bedingung könnte eine kaputte englische Liste unbemerkt null Treffer liefern — der Roundtrip
allein würde das nicht merken.

### Ein Name, drei Verwendungen

Bei der Kosmetik stand jeder der 27 Namen **dreimal** im Code: als Kartenrücken, als Spielfeld
(„Kitsune · Battlefield") und als kaufbares Paket. Ein Umbenennen hätte zwei Stellen zurückgelassen.
Das ist vor der Übersetzung repariert worden — Spielfeld- und Paketname leiten sich jetzt im
Register vom Decknamen ab (`bfName()` / `packName()`), das Suffix ist der einzige eigene Text.
Dadurch gibt es auch auf der englischen Seite genau **einen** Namen je Set statt drei.

### Verschachtelte Register: EIN Walker statt zweier Spiegelbilder

Die vier Archetyp-Leitfäden sind keine flachen Listen, sondern Bäume (Säulen, Kreislauf-Knoten,
Status-Leisten, Prinzipien). Sie Feld für Feld in Schlüssel zu übertragen hieße, die Struktur
**zweimal** zu beschreiben — einmal beim Erzeugen der deutschen Schlüssel, einmal beim Zurücklesen.
Zwei Spiegelbilder driften.

Stattdessen gibt es einen einzigen rekursiven Walker (`src/i18n/guideWalk.js`): `guideStrings()`
sammelt, `guideDef()` ersetzt — derselbe Code, also zwangsläufig dieselben Pfade. Ein neues Feld in
einem Leitfaden ist damit automatisch erfasst. Nicht-Text-Felder (Farbe, Icon, Fraktions-Zuordnung)
stehen in einer Ausnahmeliste, sonst landeten Hex-Codes im Katalog.

**Zyklus-Falle dabei:** Der Walker darf `t` NICHT importieren, weil `de.js` ihn benutzt
(de.js → guideText → index.js → de.js). Deshalb liegt der reine Durchlauf in `guideWalk.js` und
die Auflösung eine Ebene darüber in `guideText.js`.

**Die Reihenfolge, in der migriert wurde** (falls je ein weiteres Register dazukommt): erst die
Register, deren Namen in FREMDE Texte eingesetzt werden (Rarität, Formationen), dann die
selbsttragenden (Skills, Perks, Familien, Gebäude), dann das Glossar — der Sonderfall, weil seine
Texte beim Modul-Laden als Template-Literale gebaut werden und gleichzeitig auf lazy umgestellt
werden mussten —, zuletzt die UI Bildschirm für Bildschirm entlang der Spielschleife: Leisten →
Stichspiel → Entscheidungen → Architekt → Auswertung → Menüs.

**Ein Helfer für den Weg dorthin:** `node scripts/loc-todo.mjs <datei>` listet für eine UI-Datei
genau die Texte, die die Ratsche einfordert — dieselben Regeln wie der Test, an einer Stelle.
Nach der Migration meldet er `Summe: 0`; erst dann gehört die Datei in `MIGRATED`.

## 7. Werkzeug

```
npm run loc:export     # CSV neu erzeugen (docs/localization/strings_*.csv)
npm test               # inkl. i18n-Guards
```

Die CSV hat zwei Zeilenarten: `status=done` (aus dem Katalog, beide Sprachen gefüllt) und
`status=n/a` (die Musiktitel — Eigennamen, bewusst einsprachig). Die frühere dritte Art
`status=new` (heuristisch aus der JSX gefischt, `en` leer) ist mit der abgeschlossenen Migration
verschwunden; der Exporter durchsucht die JSX gar nicht mehr, weil er dort nur noch
Katalog-Schlüssel gefunden hätte.

Ein Sonderfall bleibt: die Glossar-`match`-Zeilen sind kein Anzeigetext, sondern Wortformen für
die Auto-Fettung — die müssen für Englisch **neu geschrieben**, nicht übersetzt werden.
